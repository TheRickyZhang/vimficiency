Vimfy watches how you edit and surfaces shorter keystroke sequences that
produce the same result. You keep editing Vim the way you already do — it
surfaces better motions in the background and lets you replay them side-by-side
to learn.


==============================================================================
1. Installation                                     *vimficiency-installation*

For requirements, plugin-manager snippets (lazy.nvim, packer, vim-plug), and
manual-build instructions, see the top-level `README.md`. That is the canonical
install reference; this page only covers what comes _after_ the library is
built.


SETUP

>lua
    require('vimficiency').setup()
<

For a complete setup with configuration and keymaps, use `examples/config.lua`
as the canonical sample.

You can pass config overrides to `setup{}` — see 9. Configuration.

Bind keys with a `<Cmd>Vimfy ...<CR>` map; see the full writeup in 8. Keymaps.


VERIFYING INSTALLATION

>vim
    :Vimfy help
<

If this prints the command list, you’re ready.

If instead you see "command not defined", `setup()` didn’t run — check your
config for syntax errors or a load-order issue, or see 14. Troubleshooting.

If you see an "ABI mismatch" error on load, the shared library is stale against
the Lua FFI bindings — rebuild the plugin (`:Lazy build vimficiency` or
`./scripts/install.sh` in the plugin directory). The script downloads the
prebuilt library and journal scorer for your platform when the checkout is on a
release tag and builds from source otherwise.

2. The core idea: a session              *vimficiency-the-core-idea-a-session*

Everything in Vimfy is organized around **sessions**. A session captures:

- The buffer content at a starting point
- The keys you typed
- The buffer content at an ending point

Vimfy then runs an optimizer and compares your effort with the efforts of the
best sequences it found.


THE 2×2 MATRIX OF SESSION TYPES

Every session is bounded by a **start** and an **end**. Each of those can be
picked manually (by you) or automatically (by triggers from your
configuration). The four types have distinct names, and manual invoking is
outlined here:

  ------------------------------------------------------------------------
               Manual end                     Auto end (idle trigger)
  ------------ ------------------------------ ----------------------------
  Manual start Mark — :Vimfy start <alias>,   Watch — :Vimfy watch <alias>
               :Vimfy finish <alias>          

  Auto start   Recall — :Vimfy recall N /     Suggest — fires on its own
               recall Ns                      while you edit
  ------------------------------------------------------------------------
See the per-type pages for details:

- 3. Mark — manual start, manual end.
- 4. Watch — manual start, auto end.
- 5. Recall — auto start, manual end.
- 6. Suggest — auto start, auto end.


WHERE A SESSION LIVES

Once finished, a session is **active** in memory, keyed by its alias, and
**saved** to disk under a filename of its own. Mark and Watch share a cap of
100 active named sessions, and Recall entries age out of the rolling ring.

**Pin** a session to keep a copy under a filename you choose, and **view** it
whether it’s in memory or on disk. See 7a. Session storage for the full
model.

3. Mark (manual start, manual end)  *vimficiency-mark-manual-start-manual-end*

Use these when you want precision analyzing a specific sequence or know _in
advance_ the entire sequence you want optimized.

>vim
    :Vimfy start a       " Mark the start
    " ... edit normally, any number of keystrokes ...
    :Vimfy finish a      " Mark the finish, show suggestions
<

Marks are similar semantics to marks in vim, where start/end is similar to
creating a mark and jumping back to it. However, our aliases can be any
combination of letters, ex: `a`, `refactor`, `WIP`. - Up to 100 named sessions
can be active at once across Mark and Watch. - Starting a session at an
already-used alias overwrites it. - Sessions left idle for 5 minutes, or whose
parameters would otherwise result in an invalid optimize query, are dropped
automatically. - Alternatively, you can call `vim :Vimfy close a` to drop the
session manually.


SEE ALSO

- 7. Inspecting results — how to read the output and replay
    the suggestions.
- 8. Binding keys — bind `<Cmd>Vimfy start a<CR>` /
    `<Cmd>Vimfy finish a<CR>` so your session markers don’t need typing `:Vimfy ...`.

4. Watch (manual start, auto end)    *vimficiency-watch-manual-start-auto-end*

Use this when you know the starting point but don’t want to remember to call
`:Vimfy finish` — the end fires on its own after an idle pause.

>vim
    :Vimfy watch a       " Mark the start
    " ... edit normally, then pause for `watch.idle.ms` ms ...
    " Vimfy finishes automatically and shows the result.
<

Watch must be configured before use:

>lua
    require('vimficiency').setup({
        watch = {
            idle = { ms = 3000 },
            cooldown_ms = 5000,
        },
    })
<

Watch currently supports the `idle` trigger only. The `keys` and `cost`
triggers shipped for Suggest don’t yet apply here — the manual-start side
of Watch doesn’t benefit from command-count or cost-ratio firing the way
Suggest’s auto-start side does. Ask if you’d use them and we can extend.

- Configuration parameters: see Idle end-detection
- Aliases follow the Mark grammar (letters only). `:Vimfy close a` aborts without optimizing.
- Re-issuing `:Vimfy watch a` on an active alias overwrites — the old timer is cancelled cleanly.
- The Mark auto-drop guards (idle / drift) apply here too; see Mark.


SEE ALSO

- 8. Binding keys — bind `<Cmd>Vimfy watch a<CR>`.
- 9. Configuration — full shape of the `watch` key in `setup{}`.

5. Recall (auto start, manual end)  *vimficiency-recall-auto-start-manual-end*

Recall lets you look backward without any previous marking setup by querying a
continuously maintained queue. It is always on — the bounded, RAM-only ring
is foundational enough that there’s no toggle.

>vim
    " ... edit normally ...
    :Vimfy recall 6       " Analyze the last 6 commands
    :Vimfy recall 3s      " Analyze the last 3 seconds
<

`:Vimfy finish <alias>` stays reserved for manual handles (Mark / Watch);
retrospective windows go through `:Vimfy recall`.


WINDOW ALIASES: TWO WAYS TO INDEX THE QUEUE

  -----------------------------------------------------------------------
  Syntax   Meaning                 Use when
  -------- ----------------------- --------------------------------------
  N        Last N commands         You can estimate how many commands the
                                   edit took

  Ns       Last N seconds of       You can estimate time better than key
           activity                count
  -----------------------------------------------------------------------
Both forms are measured back from _now_, and name the **whole span** up to that
point — not a fixed-size window floating in the past. `3s` analyzes
everything typed in the last 3 seconds (the range from 3s-ago through the
present), and `50` the last 50 commands. The number sets how far _back_ the
range reaches; the range always ends at the current cursor.

Mixing forms (`3m`, `3ms`, `2h`, etc.) is not supported. Seconds is the only
time unit; if you want 90 seconds, use `90s`.

The same grammar is reused by Suggest triggers (e.g. `window = "3s"` / `"50"`)
— anywhere Vimfy wants a slice of the queue, `N` and `Ns` are how you name
it.


IMPLEMENTATION DETAILS

Each command is tagged with a timestamp. `:Vimfy recall Ns` resolves to the
most recent commands run within the last `N` seconds. If a command or time
cutoff falls inside a burst delivered together, Recall includes the whole
burst. For example, `recall 1` can include both deletions in `dwdw` when Neovim
reported only their combined result.

The ring shares command observations and changed lines across overlapping
recall windows. Finishing a window submits its observed range to the optimizer.


CAPACITY

The queue is bounded by two caps, applied with **union semantics** — a
session is kept as long as EITHER cap still holds it, and only evicted when
BOTH say drop:

  ------------------------------------------------------------------------
  Knob                      Default   Meaning
  ------------------------- --------- ------------------------------------
  KEY_SESSION_CAPACITY      200       Count floor: keep at least N
                                      sessions.

  MAX_RETENTION_SECONDS     120       Age floor: keep sessions newer than
                                      N.
  ------------------------------------------------------------------------
So at defaults, the queue always retains at least 200 sessions AND at least the
last 120 seconds of activity.

>lua
    require('vimficiency').setup({
      KEY_SESSION_CAPACITY  = 500,   -- keep more sessions
      MAX_RETENTION_SECONDS = 300,   -- keep a longer time window
    })
<

If `recall Ns` asks for a window older than the queue retains, the alias fails
to resolve and you get "No recall session found within 'Ns'…" — raise
either cap.

The recall ring is discarded when Neovim exits. A window you finished with
`:Vimfy recall` is saved to disk like any other session.


RECALL ALIASES MOVE

Recall windows rotate out of the queue as you type, so an alias like `3s` soon
names something else. `@` refers to the most recently ended session, which
makes it the handle to pin one by:

>vim
    :Vimfy recall 3s
    :Vimfy pin @ nested-refactor
<

6. Suggest (auto start, auto end)    *vimficiency-suggest-auto-start-auto-end*

Suggest runs the optimizer on its own and surfaces a result without you calling
`:Vimfy finish` or `:Vimfy recall`. It reuses the recall queue for the start
and fires on triggers you configure.


ZERO-CONFIG DEFAULT

You don’t need to configure anything to try it:

>vim
    :Vimfy suggest on
<

With no `auto_suggest` block in `setup{}`, Suggest arms a built-in **cost
gate** (`auto_suggest.default_cost`, default `{ m = 1.5, b = 2.0, ms = 1000,
window = "3s" }`): after a brief idle pause it analyzes the last ~3s of editing
and surfaces a result only when your typed effort exceeds `1.5 * optimal + 2`.
The toast is compact — `<your keys> (<your cost>) → <suggested keys> (<best
cost>)` — and the result is already saved as a session, reachable with the
`$` alias (the most recent suggestion):

>vim
    :Vimfy view $           " side-by-side: before/after buffer + your vs suggested sequences
    :Vimfy explore $        " step through interactively
    :Vimfy pin $            " keep a copy as pinned/suggest-<date>-<time>.json
<

`$` is a slot, not a history: the next suggestion replaces it. Older
suggestions stay listed in `:Vimfy list` until the recall ring rotates them
out.

Every suggestion is also saved to disk as it finishes and listed in `:Vimfy
stats`. Pin the ones you want to find by name.

To tune this gate, set `auto_suggest = { default_cost = { ... } }` (any subset
merges over the defaults) — this alone does not auto-enable at startup. To
auto-enable at startup, add a real trigger (`idle`/`keys`/`cost`, below).
Setting `auto_suggest = false` turns the feature off entirely, and `:Vimfy
suggest on` will refuse.


CONFIGURED TRIGGERS

>lua
    require('vimficiency').setup({
        auto_suggest = {
            idle = { ms = 3000, window = "3s" },
            keys = { every = 50 },              -- every 50 commands
            cost = { m = 1.5, b = 2.0, ms = 300, window = "100" },
            cooldown_ms = 5000,                 -- how often the optimizer may run
            notif_cooldown_ms = 2000,           -- min gap between *shown* toasts
        },
    })
<

Any subset of triggers may be configured; presence of the sub-table enables the
trigger. Omit the sub-table to disable that trigger. Configuring any trigger
also auto-enables Suggest at startup (no `:Vimfy suggest on` needed) — this
is the way to make it **default on**.

Because Suggest is (auto, auto), both halves have a config pointer:

- **Start scope** (`window`) — slice of the recall queue to analyze.
    Grammar + semantics: see Window aliases.
    `keys` has no separate window knob — the analysis slice is always
    `every` commands.
- **End trigger** (`ms`, `every`, `cooldown_ms`) — when Suggest fires.
    Idle/cost share the end-detection policy with Watch: see Idle
    end-detection <09-configuration.md#idle-end-detection>.


TRIGGERS

  --------------------------------------------------------------------------
  Trigger   Fires when
  --------- ----------------------------------------------------------------
  idle      You’ve been idle for idle.ms milliseconds.

  keys      Every keys.every real commands.

  cost      After cost.ms idle, iff user_cost > cost.m * optimal + cost.b.
  --------------------------------------------------------------------------

IDLE = { MS, WINDOW } ~

Fires on a pure pause. `window` is the analysis slice — everything back to
`window` ago (e.g. `"3s"` = all keys in the last 3 seconds), not a fixed-size
window anchored in the past. Specify the full trigger object when `idle` is
present.


KEYS = { EVERY } ~

Fires every `every` real user commands (one captured `CmdAtom` each). The
analysis slice is always the last `every` commands — a separate `window`
would collapse to the same value, so it’s not a knob.


COST = { M, B, MS, WINDOW } ~

The most selective trigger: only surfaces a result when your typed cost exceeds
the optimal by a configurable margin. Because it runs the optimizer, it’s
idle-gated on `cost.ms` — the check only runs at micro-pauses between
commands, not on every command.


  **v1 caveat.** Cost runs the optimizer synchronously on the idle tick. With
  `idle.ms = 3000` and `cost.ms = 300` armed together a 3s pause will re-run the
  analyzer every 300ms until the cooldown elapses. Acceptable for v1; the ADR
  describes a debounced-subprocess plan if this shows up as a measured cost.

DEDUP

Beyond `cooldown_ms`, Suggest also fingerprints the computed result (edit
region + user sequence + top suggestion) and suppresses a fire whose result
matches the previously shown one. The fingerprint resets when you disable
Suggest.

`notif_cooldown_ms` is a separate, finer guard at the notification layer: a
suggestion landing within that window of the previous _shown_ toast is not
displayed. It is still finished and stored, so it stays reachable via `$` and
`:Vimfy list` — only the toast is dropped. This lets you lower `cooldown_ms`
(so the optimizer keeps re-analyzing as you work) without the toasts becoming
spammy.

For `cooldown_ms` and the `idle.ms` threshold itself, see Idle end-detection
<09-configuration.md#idle-end-detection> — Watch and Suggest share that
policy.


RUNTIME ON/OFF

>vim
    :Vimfy suggest on        " enable (uses configured triggers, else the default cost gate)
    :Vimfy suggest off       " suppress firing; config untouched
    :Vimfy suggest toggle
<

If `setup{}` provides an `auto_suggest` block with triggers, Suggest is enabled
automatically at startup. With no block, it stays off until you run `:Vimfy
suggest on`, which falls back to the zero-config cost gate above.


RELATIONSHIP TO THE RECALL QUEUE

Suggest queries the same queue as Recall. Recall is always on, so there’s
nothing to configure for it separately.

7. Inspecting results                         *vimficiency-inspecting-results*


READING THE NOTIFICATION

When a session completes, you get something like:

>
    vimfy finished [a] (0,0) -> (2,2)
      user: cw xxx <Esc> jj ci yyy <Esc> (15.00)
      1. 3rx <C-d> ciw yyy <Esc> (8.00)
      2. 3rx w <C-d> 3ry (11.00)
      3. 3rx Wlj ciw yyy <Esc> (13.00)
<

- `(0,0) -> (2,2)` — cursor moved from row 0 col 0 to row 2 col 2 (0-indexed)
- `user:` — what you typed for reference
- Numbered lines — the top optimal sequences in order of cost.
- The decimal value in parentheses is the calculated effort for the corresponding sequence

Cost is a keyboard-effort score (lower is better), not a keystroke count. See
10. The effort model for how it’s computed and how to tune it to your layout.


VIEWING A RESULT

`:Vimfy view <alias> [count]` opens a new tab with side-by-side windows and
shows your recording alongside simulated optimizer suggestions. `count` sets
the number of panes, up to four. The default layout pairs your recording with
the best suggestion.

Replay opens after a brief precompute phase. Step forward with `<Right>`, back
with `<Left>`. Close the replay with `q`.

The `[you] Recorded` pane shows the text, cursor and mode Neovim reported. A
Visual deletion such as `Vd` shows the line disappearing in one step. When
several commands arrive together, one step shows their combined result. Plugin
edits appear as they happened, even when a mapping’s reported keys omit some
of the text it inserted.

Each numbered `Simulated` pane runs a suggestion in a hidden Neovim buffer. You
can compare the two even when you used the same keys as the top suggestion.
Both panes use the same slice, including lines you visited and temporary edits
you later undid. A step advances each pane to its next available state.

Opening an older v1 save shows a warning. Its user pane has one step between
the two states that file contains. Suggestions still animate normally.

Each replay window shows a virtual header above the buffer:

- progress through the global and local step counts, plus the current
    editor mode
- the replay sequence itself, wrapped to the window width, with the
    current token highlighted

The `[N]` label at the start of the currently-focused window’s header is
colored distinctly, so a glance at the tab tells you which buffer your cursor
is in. The cursor highlight also changes with the simulated mode, so insert and
visual segments are visible even in unfocused windows.

`<Tab>` / `<S-Tab>` cycle between the sim sequences: in the split layout they
move the cursor to the next/previous sim window (wrapping); in focus mode they
swap the displayed buffer in place. `<CR>` toggles focus on the window under
the cursor — it collapses the tab to just that window full-screen, and `<CR>`
again from inside restores the side-by-side layout. The same toggles are also
available as `:Vimfy focus <N>` / `:Vimfy escape` for typed invocation.


REPLAY BUFFER KEYS

Press |g?| in a replay buffer to open this section directly.

- `<Left>` — step backward
- `<Right>` — step forward
- `<CR>` — focus or unfocus the current replay buffer
- `<Tab>` / `<S-Tab>` — cycle to the next or previous replay sequence
- `<leader>y` — yank the current window’s sequence into the unnamed and `+` registers
- `?` — show the short keymap summary popup
- `g?` — open the full help section for replay buffers
- `q` — close the replay tab


LISTING WHAT’S AROUND

>vim
    :Vimfy list
<

Shows the active sessions and the pins.


SAVED SESSIONS AND PINS

Every finished session is active in memory until it rotates out, and is saved
to disk as it finishes. `:Vimfy pin` keeps a copy under a filename you choose.

`:Vimfy view <alias>|<filename>` works against all three: it replays from
memory first, then a pin, then a saved session. Tab completion on `:Vimfy view`
lists the aliases and pins.

See 7a. Session storage for the full model and a worked example.

8. Binding keys to Vimfy actions   *vimficiency-binding-keys-to-vimfy-actions*

Vimfy measures the keys you type, but a key that _invokes_ Vimfy is never
mistaken for motion. Capture runs off Neovim’s per-command `CmdAtom` event,
which reports the resolved action: a binding that runs a `:Vimfy` command (or
any Lua that doesn’t edit the buffer) produces an inert event and is excluded
automatically.

So there is no special binding API — use whatever Vim already gives you.


VIM.KEYMAP.SET WITH A <CMD> MAP (RECOMMENDED)

Bind the LHS to the `:Vimfy` command directly:

>lua
    vim.keymap.set('n', '<leader>vs', '<Cmd>Vimfy start a<CR>',   { silent = true })
    vim.keymap.set('n', '<leader>vf', '<Cmd>Vimfy finish a<CR>',  { silent = true })
    vim.keymap.set('n', '<leader>vq', '<Cmd>Vimfy pin @ quick<CR>', { silent = true })
<

Everything after `Vimfy` is the subcommand and its arguments, exactly as
you’d type `:Vimfy ...`. `<Cmd>` runs it without leaving normal mode, and the
keypress is never recorded as motion.

In vimscript the equivalent is `nnoremap <leader>vs <Cmd>Vimfy start a<CR>`.


BINDING ARBITRARY LUA ~

Use a function RHS when you need to branch or compose:

>lua
    vim.keymap.set('n', 'Z', function()
      if vim.bo.buftype == "" then
        vim.cmd('Vimfy start a')
      end
    end)
<

As long as the callback doesn’t edit the buffer, pressing `Z` is not recorded
as motion.


DIRECT :VIMFY ... TYPING AND EX-COMMAND MAPS

Both work as-is. Typing `:Vimfy ...` is never counted as motion, and neither is
a mapping whose RHS is a literal Ex command:

>vim
    nnoremap X :Vimfy start a<CR>
<

Because the `CmdAtom` event reports the resolved command rather than the raw
keystroke, the `X` press is recognized as a non-editing action and excluded.

9. Configuration                                   *vimficiency-configuration*

All settings are optional, and this page documents each one in detail. For a
copy-pasteable starting point with recommended keymaps, see
`examples/config.lua` — it sets the common toggles at their defaults and
points back here for the advanced knobs.

Minimal setup:

>lua
    require('vimficiency').setup()
<

Unknown keys produce a loud warning at setup — typos don’t silently no-op.


SEARCH AND PERFORMANCE

The optimizer runs **synchronously on Neovim’s main thread**, so each run
blocks the editor until it returns. These knobs bound how much work a run does
— reach for them first if Suggest or interactive Explore ever feels laggy.
All are optional and default as shown.

  ------------------------------------------------------------------------
  Field                Default                   Meaning
  -------------------- ------------------------- -------------------------
  MAX_SEARCH_LINES     500                       Hard ceiling on the
                                                 analyzed slice height. A
                                                 region taller than this
                                                 is skipped entirely
                                                 instead of analyzed — the
                                                 strongest guard against a
                                                 runaway search. Lower it
                                                 to cap worst-case
                                                 latency.

  SLICE_PADDING        5                         Context lines included
                                                 above and below the
                                                 detected edit region
                                                 before searching. More
                                                 padding means a larger
                                                 search.

  RESULTS_CALCULATED   20                        How many candidate
                                                 sequences the search
                                                 computes per run.

  RESULTS_SAVED        5                         How many of those
                                                 candidates are kept and
                                                 shown.
  ------------------------------------------------------------------------

OPTIMIZER OVERRIDES

`optimizer = { ... }` forwards low-level A* parameters to **every** optimizer
call (mark, watch, recall, suggest, and explore defaults). Leave it empty to
use the built-in defaults; set only the keys you want to change. Confirm the
values actually in effect with `:Vimfy config`.

  ------------------------------------------------------------------------------
  Key              Default                     Meaning
  ---------------- --------------------------- ---------------------------------
  maxNodesPopped   50000                       A* search budget — the most
                                               states the search will expand
                                               before stopping. The main lever
                                               for per-run cost; lower it to
                                               trade thoroughness for speed.

  maxResults       20                          Upper bound on results retained
                                               inside the search.

  effortWeight     1.0                         Weight on keystroke effort in the
                                               cost function.

  distanceWeight   1.0                         Weight on the distance-to-goal
                                               heuristic. Set to 0 for an exact
                                               Dijkstra search — guaranteed
                                               cheapest result, but slower.

  exploreFactor    2.0                         Effort cutoff multiplier: the
                                               search only keeps candidate
                                               sequences whose effort is at most
                                               exploreFactor × your typed effort
                                               (default 2.0 = up to twice as
                                               costly). Lower it to prune the
                                               search harder (faster, but may
                                               discard distant alternatives).

  minPrefixCount / 4 / 16                      Range of count prefixes the
  maxPrefixCount                               search tries (e.g. 3w). Setting
                                               minPrefixCount > maxPrefixCount
                                               disables count-prefixed
                                               exploration while leaving
                                               unprefixed search intact.
  ------------------------------------------------------------------------------
The distance heuristic is intentionally inadmissible (it can overestimate), so
a higher `distanceWeight` searches faster but may miss the cheapest sequence;
`distanceWeight = 0` recovers optimality at the cost of speed.

The search for each individual edit has its own `distanceWeight`, `0.35`, which
this key does not change.


RECALL AND SESSION SAFETY

Recall keeps a rolling ring of recent commands so you can analyze "N commands /
Ns ago" after the fact. These knobs bound that ring and the lifetime of
in-progress sessions.

  ---------------------------------------------------------------------------------
  Field                         Default                   Meaning
  ----------------------------- ------------------------- -------------------------
  KEY_SESSION_CAPACITY          200                       Number of recent commands
                                                          always kept once
                                                          captured.

  MAX_RETENTION_SECONDS         120                       Age in seconds before a
                                                          Recall entry can be
                                                          evicted. An older entry
                                                          is evicted only when the
                                                          ring also exceeds
                                                          KEY_SESSION_CAPACITY.

  MANUAL_IDLE_TIMEOUT_SECONDS   300                       A manual (start/finish)
                                                          session left idle this
                                                          long is auto-ended with a
                                                          warning.

  lossy_mappings                "warn"                    For a Lua mapping that
                                                          moves the cursor or edits
                                                          text, "drop" ends the
                                                          session and names the
                                                          mapping. "warn" records
                                                          its typed keys with a
                                                          once-per-session notice.
                                                          "allow" records silently.
                                                          View shows the observed
                                                          cursor and edit under
                                                          those keys.
  ---------------------------------------------------------------------------------

SAVED SESSIONS

Every finished session’s result is written to
`stdpath('data')/vimficiency/sessions/`, so `:Vimfy stats` can show and replay
it later. See 7a. Session storage.

A result holds the lines its session ran over, unencrypted. That is the part of
the buffer the session touched plus a few lines of context, which for a small
file is all of it.

>lua
    require('vimficiency').setup({ sessions = { save = false } })
<

  -----------------------------------------------------------------------------
  Field               Default                   Meaning
  ------------------- ------------------------- -------------------------------
  sessions.save       true                      Save every finished session’s
                                                result. Nothing is removed on
                                                its own; :Vimfy rm deletes one.
                                                When off, a result lives only
                                                in memory unless you
                                                :Vimfy pin <alias> <filename>
                                                it.

  -----------------------------------------------------------------------------

JOURNAL

The journal continuously records everything Vimfy captures, so sessions can be
cut from it later. It is off by default because it writes the text of every
buffer you edit to disk, unencrypted.

>lua
    require('vimficiency').setup({ journal = { enabled = true } })
<

  -----------------------------------------------------------------------------------
  Field                           Default                   Meaning
  ------------------------------- ------------------------- -------------------------

IDLE END-DETECTION

Two features auto-fire on command idleness: Watch (ends a manual session once
you pause) and Suggest’s `idle` / `cost` triggers (run the optimizer on a
window of the recall queue). Both use the same engine but run independently —
each owns its own timer and cooldown, configured under its own key.

  -----------------------------------------------------------------------
  Parameter                     Meaning
  ----------------------------- -----------------------------------------
  watch.idle.ms /               Real command idleness, in ms, before the
  auto_suggest.idle.ms          trigger fires.

  auto_suggest.cost.ms          Same semantic as idle.ms but dedicated to
                                the cost trigger.

  watch.cooldown_ms /           Minimum time between consecutive fires.
  auto_suggest.cooldown_ms      Safety rail for low idle.ms.
  -----------------------------------------------------------------------
"Real command" excludes cmdline input and Vimfy admin actions, so `:Vimfy`
commands and `<Cmd>Vimfy`-routed bindings don’t reset the idle timer.

A bare `ms` inside any trigger object universally means "idle threshold" —
fire only after N ms of no activity. `keys.every` is the one exception: it
counts commands, not time, so it has no `ms`.

EFFORT MODEL TUNING

The optimizer scores sequences by a keyboard-effort model with several tunable
knobs: per-key base costs, same-finger / same-key / alt-hand / good-roll /
bad-roll weights, and count-penalty overrides. These are accepted in `setup{}`
but documented separately — see 10. The effort model.

10. The effort model                            *vimficiency-the-effort-model*


  **Status: placeholder.** The effort model is a substantial topic — this page
  will grow. For now, use `:Vimfy config` to inspect the live values and the
  pointers below to understand the shape.
Vimfy does not score sequences by keystroke count. It scores them by **keyboard
effort**: how hard each key is to reach, whether consecutive keys involve the
same finger, whether they alternate hands, etc. A 4-key sequence using good
rolls on the home row can be "cheaper" than a 3-key sequence that repeats the
pinky.


WHAT’S TUNABLE

The following knobs are accepted by `setup{}`; see their live values with
`:Vimfy config`.


GLOBAL WEIGHTS (WEIGHTS) ~

>lua
    require('vimficiency').setup({
      weights = {
        key_weight         = 1.0,   -- baseline per-keystroke cost
        same_finger_weight = 1.0,   -- penalty for two different keys on one finger
        same_key_weight    = 1.0,   -- penalty for the same key twice
        alt_hand_weight    = 1.0,   -- bonus for alternating hands
        good_roll_weight   = 1.0,   -- bonus for inward rolls
        bad_roll_weight    = 1.0,   -- penalty for outward rolls
      },
    })
<


PER-KEY BASE COST AND FINGER/HAND ASSIGNMENT (KEYS) ~

Each of the 61 keys on the modeled layout has `{hand, finger, base_cost}`.
Default is QWERTY; override specific keys to retune for your own layout. (A
fuller "layout file" API is planned — for now, override the key table entries
directly by index.)


COUNT-PENALTY OVERRIDES (COUNT_PENALTY_OVERRIDES) ~

A count prefix like `8j` is cheaper than eight `j`s but not free. The penalty
grows with count (concavely: each extra unit costs less than the last) and
motion span. Per count-class overrides let you reshape this curve.

ALIASES AND FILENAMES

Every handle you type is either an **alias** (a session in memory) or a
**filename** (a result on disk: a pin, or a saved session).

  -----------------------------------------------------------------------
  Alias      Means
  ---------- ------------------------------------------------------------
  a, foo     Letters only → a named alias, like a named register.

  6          Digits → recall N commands ago.

  3s         Digits + s → recall N seconds ago (see 5. Recall).

  @          The most recently finished session.

  $          The most recent auto-suggest regression.
  -----------------------------------------------------------------------
Which aliases a subcommand accepts:

  -----------------------------------------------------------------------
  Subcommand                Accepts
  ------------------------- ---------------------------------------------
  start / watch / finish    A named alias.

  recall                    N or Ns.

  close                     Any alias.

  view / explore / pin      Any alias or a filename (memory first, then
                            pins, then saved sessions).

  unpin                     A pin’s filename.

  rm                        A saved session’s filename.
  -----------------------------------------------------------------------
`@` is handy when the session you want to keep is a recall window whose alias
(`3s`) is moving out from under you:

>
    :Vimfy recall 3s
    :Vimfy pin @ nested-refactor
<

`:Vimficiency` is accepted as a full-name alias for `:Vimfy`.


ACTIVE, SAVED, PINNED

A finished session is **active** in memory under its alias, and **saved** to
disk under a filename made from the alias and the finish time. `pin` keeps a
copy that stays until you `unpin` it.

The same text can be an alias and a filename. See 7a. Session storage for the
full model.


SESSION PICKER (:VIMFY LIST)

Opens a centered float with two panes — **Active** (in-memory sessions) and
**Pinned** (files under `stdpath("data")/vimficiency/pinned`) — and a
live-filter prompt at the bottom. `<Tab>` toggles between panes.

Ongoing sessions always sit in a pinned **Ongoing** section at the top,
regardless of sort mode. Auto-generated recall ring entries (one per command)
are folded into a single `recall ring (N)` summary row — the per-entry
aliases drift, so they’re not individually actionable from the picker;
resolve a specific window with `:Vimfy recall N` or `:Vimfy recall Ns` instead.

  Key        Action
  ---------- ------------------------------------------------
  /          Fuzzy-filter by alias (prompt at bottom, live)
  <CR>       Open (default action, see below)
  <Tab>      Switch Active ↔ Pinned pane
  sn/sN      Sort by name (A→Z / Z→A)
  sc/sC      Sort by category (A→Z / Z→A)
  st/sT      Sort by time (newest / oldest)
  s          Sort hint popup (also on s?)
  d          Delete the current entry
  m          Toggle mark on the current entry
  D          Delete all marked entries
  r          Rename (see below)
  y          Duplicate (see below)
  ?          Show the keymap popup
  q, <Esc>   Close
Inside the search prompt, `<C-n>` / `<C-p>` (and `<Down>` / `<Up>`) move the
list cursor without leaving insert mode; `<CR>` opens the current entry;
`<Esc>` returns to the list.

**Per-pane action semantics:**

- `<CR>` — on either pane, opens it as `:Vimfy view` does: a finished
    session on Active, the pin on Pinned.
- `d` — on Active, discards the session (equivalent to `:Vimfy close`);
    on Pinned, unpins (equivalent to `:Vimfy unpin`).
- `r` / `y` — on Pinned, renames/duplicates the file. On Active, renames
    the named alias / registers a duplicate finished record under a new
    alias. Only entries with a stable name alias are renameable this
    way; for recall and auto-suggest results, pin first (`:Vimfy pin <alias> <filename>`) and then rename from the Pinned pane.

**Blocked on in-progress sessions:** `<CR>`, `r`, `y` all refuse to run on a
still-accumulating session. Finish it with `:Vimfy finish` (or let Watch’s
idle trigger fire) and try again.


SESSION STATS (:VIMFY STATS)

Opens a tab with a header over one full-width pane:

- **Header** — the scorings counted, the weight and the charted run length,
    over the path of the session log the stats are read from.
- **Stats** — a Sessions band over a Journal band, with a faint line between
    them (`VimficiencyStatsRule`). Each holds its efficiency chart, its
    optimizer times and its own Commands tables.

In a wide window a band’s Commands tables sit to the right of its chart, and
in a narrow one under it. `l` from the left side goes to that band’s first
command, and `h` from a command goes back to its chart.

The stats are laid out as items: rows that list runs or expand command lists,
charts, and selector rows. One item is always current. It is highlighted whole
and the cursor itself is hidden.

`h`, `j`, `k` and `l` move to the item on that side, and the other keys act on
the current one. Any other motion takes the nearest item.

Keys in the stats (`?` lists them):

  -----------------------------------------------------------------------
  Key             Action
  --------------- -------------------------------------------------------
  j / k           The item below / above; a count moves that many.

  h / l           Change the active option on a selector row, or move to
                  the item to the left / right. The arrow keys work the
                  same way.

  <CR>            Open a row’s runs, open a full-screen chart, or expand
                  or collapse a command list.

  w               Switch the efficiency weight between effort and uniform
                  for this view.

  v               Count every scoring, or only the current one (see
                  below).

  gs              Open :Vimfy appearance.

  q               Close the tab.
  -----------------------------------------------------------------------
`<Esc>` or `q` closes the float opened by `<CR>`. A chart fills its column in
the stats and the whole screen in its float.

The stats keep each band’s left side to its headline: the Sessions
efficiency, the Journal’s run lengths, a chart each and the optimizer times.
The rest is under the chart in its float.

The chart takes up most of the float. Scroll down with `<C-d>` or the mouse
wheel to see the details below it. Moving back up to a chart bucket brings the
entire plot into view. The chart draws two lines: the efficiency, solid,
against the left axis, and the number of samples behind it, dotted, against the
right. Each bucket’s own value is a larger dot, placed to the nearest row,
and the lines only join them; the float’s title has the exact value. A line
breaks where there are no samples. Their colors are
`VimficiencyStatsEfficiency` and `VimficiencyStatsVolume`. `e` and `s` hide and
show the efficiency and the samples line. `+` shows more history and `-` shows
less, from 15 minutes to 30 weeks. These keys change the history scale of the
float. `?` lists the chart keys.

In the chart’s float each bucket with runs is an item, named with its
efficiency in the title. `h` and `l` move between buckets and `<CR>` lists the
selected bucket’s runs. The rows under the chart list their runs the same
way.

The run list floats over the tab at its full width, one line per session or
journal run: when, your effort, the best found, the saving, the extra
characters you typed in insert mode and the search time. Its title holds the
row it came from, the sort and the page. It takes two fifths of the screen and
the preview under it the rest.

The preview follows the current run. Its first line is the run’s id: a
session’s saved filename, which `view` and `pin` take, or a journal run’s
file and position.

Under the id are your keys and the best sequence, spaced by command and cut to
two lines each. Then the run’s text before and after, side by side, with the
changed lines marked and the cursor’s place shaded in each.

A session’s text comes from its saved result. A session finished before
results were saved, or with `sessions.save` off, shows its keys and why the
text is not available.

Runs from closed journals that have been idle for `journal.keep_days` and fully
scored count toward totals after rollup. Only individual runs still on disk
appear in the list.

Every cell of the list is an item, as in the stats:

  -----------------------------------------------------------------------
  Key           Action
  ------------- ---------------------------------------------------------
  j / k         The run below / above, in the same column.

  h / l         The column to the left / right. The arrow keys move the
                same way.

  s             Sort by the current column: largest first, then smallest
                first, then off. Unsorted, the worst runs come first
                (your effort minus the best).

  <CR>          Replay the run as :Vimfy view does, your keys beside what
                was found, highlighted as the file was. A session shows
                every sequence found, a journal run the best one. q there
                returns to the list.

  p             Pin the current session. Asks for the filename, which
                defaults to its saved one.

  ] / [         Next / previous page of runs.

  <Esc> / q     Back to the stats.
  -----------------------------------------------------------------------
Sections:

- **Sessions** — your percent efficiency: the best effort found over the effort
    you spent, `min(best / yours, 1)`, averaged over sessions. It never passes
    100%. A session that beats the optimizer and any unbeaten session with
    positive user effort each count as 100%. By default, sessions are
    weighted by the effort you spent. Set `stats.weight = "uniform"` to
    count each once (see
    configuration). The Look back selector sets both
    overview efficiency charts and their Commands tables to the same period
    of 30 minutes, hours, days, or weeks. The average and sample count above
    each chart cover that period.
    Its float adds the total finished sessions by type (mark / watch / recall /
    suggest) and the commands recorded in them. Its **Not scored** and
    **Unbeaten** headings have selectable categories underneath, just as in
    the Journal float.
    _You beat the optimizer_ counts the scored sessions where your keys cost
    less than the best sequence found, and `<CR>` lists them. Each is a
    sequence the search missed or one the cost model underprices.
- **Journal** — the same efficiency over everything you typed, not only
    finished sessions. Needs the journal turned on.
    See below.
- **Commands** — one set of tables per band, never added together: the
    Sessions band counts your scored sessions, and the Journal band your scored
    journal runs of the selected length, over the same Look back period as the
    chart. The line over the tables counts comparisons that have a best
    sequence. The efficiency chart also counts unbeaten runs.
    For every command that appears at least ten times across those and the
    optimizer’s best sequences for them, the ratio
    `your_share / optimizer_share`, with the two shares beside it. Three
    lists: _Underused commands_, which you use less than the optimizer
    (candidates to practice); _Overused commands_, which you use more
    (potential inefficient habits); and _Never used by the optimizer_. Each
    list starts with five rows. Press `<CR>` on
    _… and N more_ to reveal the remaining rows in place or on _Show fewer_
    to collapse them again. The target of `f`/`F`/`t`/`T`/`r`/`R` is
    collapsed to `_`, an insert counts its entry command and editing keys
    such as `<BS>` (typed characters are only totalled), and `ce`/`cw`
    share a row, as do `cE`/`cW`; the row’s run list names your split. A `gj` or `gk`
    that crossed to another line shares a row with `j` or `k`; one that
    moved along a wrapped line is listed apart, as `gj (same line)`.
    Under the lists, _Extra typed text_ is how much more you typed in insert
    mode than the best sequences did; `<CR>` lists the runs where you typed
    more.
- **Optimizer times** — under each band’s chart. Sessions: _Optimizer response_, the median response time over the last 30 days; `<CR>` lists
    those sessions, slowest first. Journal: _Movement search_ and _Composition search_, the search time for retained runs of the selected length; `<CR>`
    opens the chart. These timing views use their own samples independently
    of Look back. The Movement chart groups queries by lines from start to
    goal. The Composition chart groups queries by buffer positions in the larger
    before/after search slice. Each chart shows median milliseconds and
    sample count for searches with a recorded duration and size, including
    searches that finished without a solution. Select a bucket for its exact
    values and any deadline hits. `<CR>` lists its runs, slowest first. p95
    appears from 100 samples.

A scoring is the plugin’s scoring version plus the settings a score depends
on. The stats count sessions and rolled-up journal runs from every scoring. `v`
counts only the current one; the stats then say how many runs it hides.


THE JOURNAL SECTION ~

The journal is cut into back-to-back runs of 4, 8 and 16 commands, and each run
is scored as if you had ended a session there. A run’s score is the effort of
the best sequence found over the effort of what you typed.

In the stats:

- **Run length** — each available length in brackets, with the selected length in bold
    (8 commands by default). Use `h` or `l` on the row to switch lengths. Longer runs give the
    optimizer more to merge, so they usually score lower.
- **Percent efficiency** — the selected length’s average and sample count for the visible period. Minute and hour bars use timestamped samples. Archived daily totals also contribute to day and week bars.

If some of the journal still needs scoring under the current settings, its
coverage percentage appears above the chart in the float. The float title shows
the overall efficiency, run count and run length. A run that ends where it
started counts as all waste. Below the chart:

- **Movement only / With edits** — one bar, split by whether the text
    changed. Each caption shows efficiency, then the run count. The decimal in
    parentheses is the group’s share of all scored runs of the selected length.
    Their colors are `VimficiencyStatsMovement` and
    `VimficiencyStatsEdit`.
- **Size** — the label to the left of the ranges under the second bar,
    which uses the same size groups as the search-time charts. For movement and
    edits, size is the larger of the before and after position counts in the
    unpadded region. That region covers both
    cursor rows and all net changes. Matching rows are trimmed from the top and
    bottom up to the cursors, so inserting or deleting a line leaves an unchanged
    tail out of the count. Each byte in a line counts as one position, and an
    empty line counts as one. Runs without a recorded size are drawn shaded (`░`).
- **Not scored** — runs left out of the score, in `VimficiencyStatsNotScored`.
    The rows under it say why: the changed region was too large, the search
    found nothing, or the search failed.
- **Unbeaten** — runs where no modeled sequence came close to your keys,
    scored as 100%, in `VimficiencyStatsUnbeaten`. The rows under it count the
    runs with a bare paste (`p`, `P`, `gp`, `gP`) or undo or redo (`u`, `U`,
    `<C-r>`). A run with both counts under each. _Other_ counts runs with
    neither. Rolled-up runs contribute only to the heading total because
    their command details are gone.

`<CR>` on a row under either heading lists its runs.

Every segment of either bar is an item: `h` and `l` move along a bar, `j` and
`k` between them, and the float’s title has the segment’s efficiency and
run count. `<CR>` opens the run list for the selected segment.

A run is dropped, not scored, when the journal cannot account for everything in
it: you switched buffer or window, an ex command or mouse click changed
something, or you paused for more than 30 seconds.

The first background scoring check runs 30 seconds after startup or on an
earlier idle event. After that, Neovim checks for new journal data when idle
and starts another low-priority run at most once every five minutes. While the
worker runs, the Journal section shows the percentage of recorded journal bytes
scored under the current settings, for example `Scoring journal… 42%`. The
open Stats view checks progress once a second. The efficiency average returns
when scoring finishes.

After a settings change, the journal is rescored under the new settings. Until
that finishes, runs scored under the old settings are left out, never mixed in.
Rolled-up runs keep the scoring they were rolled up under, since their journal
is gone. `:Vimfy stats refresh` scores right away, which is also how to score
with `journal.sampling.auto = false`.


WHERE THE DATA LIVES ~

Every finished session (mark, watch, recall, suggest) is appended to
`stdpath("data")/vimficiency/sessions.vfs`, with your keys, its cost and the
single best sequence found.

Its full result, with the text it changed and every sequence found, is saved
beside the log in `sessions/` (see 7a. Session storage). The log record names
that file, which is how a run list finds a session’s text.

Each session is stamped with the scoring version and every setting its score
depends on: keyboard, effort weights and optimizer overrides. The stats count
every stamp’s sessions; `v` in the stats tab keeps only the current
stamp’s.

The JSON log of earlier versions, `sessions.jsonl`, predates stamps. It is
moved to `legacy/sessions.v1.jsonl` and no longer read.


TAB COMPLETION

Works on:

- Subcommands (`:Vimfy s<Tab>` → `start`, `stats`, `suggest`).
- Named aliases for `start`, `watch`, and `finish`.
- `3s`/`5s`/`10s`/`30s` hints for `recall`.
- Live aliases plus time hints for `close`.
- Every alias (including `@` and `$`) plus pins for `view`, `explore` and
    `pin`. Saved sessions are left out: there is one per finished session.
- Pins for `unpin`, saved filenames for `rm`.
- `on` / `off` / `toggle` for `suggest`.
- `refresh` for `stats`.

12. Recommended workflows                  *vimficiency-recommended-workflows*


“I’M ACTIVELY TRYING TO LEARN BETTER MOTIONS”

Enable Suggest and the recall queue in your config:

>lua
    require('vimficiency').setup({
        auto_suggest = { idle = { ms = 3000, window = "3s" } },
    })
<

Edit naturally. Every pause surfaces suggestions. When something catches your
eye, `:Vimfy view 3s` (or whatever window the suggestion targeted) to see it
animated.

Pair with 8. Keymaps:

>vim
    nnoremap <leader>vv <Cmd>Vimfy view a<CR>  " or ...bind to view b / view c / etc.
<

…so replaying a suggestion is a single keystroke.


“I WANT TO AUDIT A SPECIFIC EDIT I’M ABOUT TO DO”

Mark sessions give the cleanest boundaries:

>vim
    :Vimfy start a
    " ... the edit ...
    :Vimfy finish a
    :Vimfy view a
<


“I KNOW THE START BUT NOT WHEN I’LL STOP”

Watch it — same precise start, but let Vimfy auto-finish when you pause:

>lua
    require('vimficiency').setup({ watch = { idle = { ms = 3000 }, cooldown_ms = 5000 } })
<

>vim
    :Vimfy watch a
    " ... edit normally, and stop when done ...
    " ... after idle.ms of idleness, the optimizer runs and the result notifies ...
<


“I JUST DID SOMETHING CLUMSY — WAS THERE A BETTER WAY?”

Recall is built for this:

>vim
    " Recall is always recording — just query it.
    " ... clumsy edit, say 5 keys ...
    :Vimfy recall 5     " or `recall 3s` if time is the easier estimate
    :Vimfy view 5
<


“I WANT TO REVISIT THIS LATER / SHARE IT”

Pin it after finishing — `@` resolves to the session you just finished:

>vim
    :Vimfy finish a
    :Vimfy pin @ nested-dict-refactor
    " ... days later ...
    :Vimfy view nested-dict-refactor
<

Pins are durable across Neovim restarts and live in
`stdpath('data')/vimficiency/pinned/` — you can share the file directly if
you want to show a colleague.

13. Known limitations                          *vimficiency-known-limitations*

- **Needs Neovim nightly (0.13-dev).** Capture runs off the `CmdAtom` event;
    `setup()` raises on older Neovim.
- **Screen-line motions.** The optimizer approximates `gj`/`gk` as `j`/`k`. The
    recorded pane shows the cursor position Neovim observed.
- **Multi-buffer edits** aren’t supported within a single session. If you
    finish a session while a different buffer is focused, it is rejected. Transient
    window changes (floating pickers, temporary splits) are fine — the session
    stays alive and keys typed outside the session window are silently ignored.
- **Large regions** include intermediate cursor visits, edited lines and padding.
    Regions beyond `MAX_SEARCH_LINES` are refused with an error; split the edit up
    or increase the limit if you really want this.
- **Long sessions** may hit the optimizer’s search budget; expect diminishing
    suggestion quality beyond roughly a dozen lines of edits.
- **Mappings to Lua callbacks can’t be audited as motion.** A key mapped to a
    Lua function that edits the buffer or moves the cursor produces an unreplayable
    capture event. By default (`lossy_mappings = "warn"`) the keys you typed label
    the action and a once-per-session notice appears. View shows the observed
    effect, including edits made through plugin APIs. `"allow"` records silently,
    and `"drop"` ends the session with a warning that names the mapping (see
    Configuration). Mappings whose RHS is a key sequence are fine — they are
    captured as the resolved post-mapping keys. Either way your cost counts the
    keys you pressed, not what they expanded to. The optimizer uses the captured
    start and goal. Type the underlying keys directly when you want a specific
    motion audited.
- **Some recorded keys are inaccurate** until Neovim reports them per command.
    Text a Lua Insert-mode mapping inserts (nvim-ts-autotag’s `>`) is missing
    from the key label. View still shows the inserted text at the next observation.
    Your cost can be off by a key when commands arrive in one burst, or when a
    Vimscript plugin reads keys with `getchar()`.
- **Recall only records actions in normal file buffers** (`&buftype == ""`).
    Actions in help, quickfix, terminal, prompt, or scratch buffers are skipped —
    they aren’t meaningful for nav or transform optimization, and recording them
    would cause recall queries to fail with buffer-mismatch when you return to your
    file. Input typed into an async floating prompt (e.g. `vim.ui.input`
    overridden by dressing.nvim) is filtered automatically.

14. Troubleshooting                              *vimficiency-troubleshooting*

Start with `:checkhealth vimficiency`. It reports the Neovim version, whether
the native library loaded and from where, its version, and whether `setup()`
has run.


“COULD NOT LOAD LIBVIMFICIENCY” ON STARTUP

The native library is missing from `build/` in the plugin directory. Your
plugin manager’s build step did not run or failed — run it again (`:Lazy
build vimficiency`, or `./scripts/install.sh` from the plugin directory) and
read its output. Building from source needs GCC 16+ or Clang 19+ with libc++,
CMake 4.3+ and Ninja; pinning a release tag avoids the compile by downloading a
prebuilt library instead.

If you set `VIMFICIENCY_LIB_PATH`, it is tried first; make sure it points at an
existing `libvimficiency.so` / `.dylib`.


“ABI MISMATCH” ON STARTUP

The library in `build/` was built against an older `src/LuaExports/Api.def`
than the Lua code you now have, usually after updating the plugin. Rebuild or
re-download it the same way as above.


:VIMFY COMMAND ISN’T DEFINED

You forgot `require('vimficiency').setup()` in your config, or `setup` errored
— see the two sections above.


SUGGEST NEVER FIRES

- Is it configured? `auto_suggest = { idle = { ms = N, window = "..." } }`
    in `setup{}`.
- Is it enabled at runtime? `:Vimfy suggest on`.


WATCH NEVER FIRES

- Is it configured? `watch = { idle = { ms = N }, cooldown_ms = N }` in
    `setup{}`. Without this, `:Vimfy watch <alias>` errors out at call
    time.
- Does the session still exist? Check `:Vimfy list`. Window-change
    aborts, `:Vimfy close`, and the 5-minute idle / 500-line drift
    guards all tear down Watch sessions silently.


“RECORDED LUA MAPPING … AS TYPED KEYS” OR “DROPPED — LUA MAPPING …”

A key you pressed is mapped to a Lua function (flash.nvim’s `f`/`t`/`;`, a
`vim.keymap.set` callback) and Neovim cannot report replayable keys for it. The
notice names the mapping. `lossy_mappings` decides what happens: `"warn"`
(default) records the keys you typed with a once-per-session notice, `"allow"`
records them silently, `"drop"` ends the session. View shows the recorded
effect of an admitted mapping. The key label can omit work the plugin
performed. See 13. Limitations.


SUGGESTIONS LOOK WRONG OR WORSE THAN WHAT I DID

- Some motions we can’t model (screen-line motions `gj`/`gk`, and
    mappings to Lua callbacks that edit the buffer).
- Check `:Vimfy config` — a mismatched `shiftwidth` or keyboard-effort
    setting can skew the cost.
- See 13. Limitations for the full list.


SETUP() FAILS WITH “LACKS THE CMDATOM EVENT”

Capture runs off the `CmdAtom` event, which only Neovim nightly (0.13-dev)
exposes. The plugin refuses to load without it. Upgrade to a recent nightly.


“UNKNOWN CONFIG KEYS IGNORED” WARNING

Typo in a `setup{}` key. The warning names them. Cross-check against 9.
Configuration or `:Vimfy config`.


I WANT TO START OVER CLEANLY

- `:Vimfy close <alias>` throws away any active session.
- Restarting Neovim clears all in-memory state (including the recall
    ring); saved sessions and pins survive.


STILL STUCK?

Run `:Vimfy config` and capture the output along with the sequence you typed
— most triage starts there.

15. FAQ                                                      *vimficiency-faq*


DOES VIMFY SLOW DOWN NEOVIM?

No. Capture is a small Lua append per command, on the `CmdAtom` autocmd. The
optimizer only runs on `finish` (or an auto-trigger), in C++, over a snapshot.
Recall is always on and the per-command overhead stays flat.


CAN I USE IT WITH COLEMAK / DVORAK / CUSTOM LAYOUTS?

The effort model’s `keys[]` and `weights` knobs are designed for this, but
there isn’t yet a "drop-in layout" file. Override the relevant entries
manually in `setup{}` — see 10. Effort model.


DOES IT WORK IN VISUAL OR OPERATOR-PENDING MODE?

Sessions span whatever modes you’re in — the optimizer reasons about the
start-to-end delta, not mode transitions. Some mode-sensitive motions are
simplified; see 13. Limitations.


WHY DIDN’T THE “BETTER” SEQUENCE ACTUALLY GET SUGGESTED?

A few common reasons: - The optimizer’s search budget truncated before
reaching it. - A motion it would have used isn’t modeled (`gj`/`gk`, or a
mapping to a Lua callback). - Your `shiftwidth` is different from the one the
optimizer is configured with, so indent-aware motions score differently.

See 14. Troubleshooting.


CAN I EXPORT A RESULT AS SOMETHING OTHER THAN JSON?

Not today. Every finished session is written as JSON under
`stdpath('data')/vimficiency/sessions/`, and `:Vimfy pin @ my-name` copies one
to `pinned/`. Third-party tools can consume either directly.


HOW DO I REMOVE A SAVED RESULT?

>vim
    :Vimfy rm <filename>       " a saved session
    :Vimfy unpin <filename>    " a pin
<

Each tab-completes over its own filenames. Or delete the files directly from
`sessions/` or `pinned/` under `stdpath('data')/vimficiency/`.
